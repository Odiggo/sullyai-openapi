# Contract 0.3.0: server alignment before SDK generation

This pre-1.0 contract revision adds V2/V3 notes and OpenAI-compatible chat/model
operations, and corrects existing wire descriptions. Existing operation IDs and
component names are retained. The change can still alter generated SDK types;
regenerate into a reviewable SDK PR and make an independent SDK version/migration
decision before release. No existing SDK package is published by this repository.

## Server provenance and scope

Compared against `Odiggo/sullyai-copilot` commit
[`048d799ff97224b6acf73f253faeeda9cb0e621e`](https://github.com/Odiggo/sullyai-copilot/tree/048d799ff97224b6acf73f253faeeda9cb0e621e/apps/api-server).
The local `docs/sdk/sdk-openapi-additions.yml` was the starting point, then checked
against the actual source. The tracked `origin/dev` changes at review time affect
Responses internals but not the chat/notes/upload validators audited here.

Relevant source paths under `apps/api-server/src/`:

- `api/notes/notes.schemas.ts`, `api/notes/notes-v2.ts`, and `domains/note-generation/`
  define V1/V2 inputs, accepted/poll/delete envelopes and auth failures.
- `domains/note-generation-v3/` defines strict input, synchronous responses, the
  240-second default deadline, request IDs and the separate V3 error vocabulary.
- `types/noteTemplate.ts` defines nested properties, required prompts, legacy aliases,
  and maximum heading nesting depth.
- `domains/openai-compat/` defines chat params, structured output, reasoning effort,
  credential alternatives, token usage omission/nullability and SSE error frames.
- `api/audio/audio.ts`, `domains/transcriptions/`, `libs/securityLib.ts`,
  `util/requestUtil.ts` and `utils/error_handler.ts` define uploads and wire envelopes.

Related server changes include [PR #10214](https://github.com/Odiggo/sullyai-copilot/pull/10214)
(response_format/named tool_choice), `49e09cd439` (billing/reasoning effort), and
[PR #10215](https://github.com/Odiggo/sullyai-copilot/pull/10215) (V3 billing meter).
This update covers the endpoints in the supplied fragment plus corrections to existing
spec operations. The newer `/openai/v1/responses` surface is outside that fragment and
is not newly added here. It needs its own audited contract update.

## Corrections that affect existing SDK types

- V1 `context` and `instructions` are optional but reject null. Omit them instead.
  Transcript length is 1–100000; context, previousNote and medicationList are limited
  to 50000 characters. `noteType.type` is required; `custom` is also supported.
- Patient demographics accept free strings, including gender; ISO dates are suggested,
  not validated by those fields. `patientInfo` can be null. Removed date/ID constraints
  must not be treated as new server guarantees.
- Note template section formatting belongs inside `properties`. Heading properties
  require `level` and `text`; text/list sections require `prompt` and `properties`, and
  list properties require `list_type`. CamelCase aliases remain supported alongside
  snake_case. Update any SDK examples based on the old flattened shape.
- V1 transcription acceptance uses `data.status: STATUS_PROCESSING`, and GET returns
  `data.transcriptionId`. Streaming tokens are at `data.token` inside the status/date
  envelope, not at the response root. `expiresIn` is optional, defaults to 60 seconds,
  and the server accepts a number from 60 to 604800.
- Credential failures are `{message}`. Legacy route errors use `{status,data,date}`;
  shared domain errors use `{error,details?}`. Consumers must select the correct error
  envelope rather than assume the old required integer `error` and string `message`.
- V2 audio option validation is HTTP 400. HTTP 422 is reserved here for unverifiable
  or unsupported duration; billing/admission can also return 402, 409 and 503.
- Norwegian language code `no` is quoted to prevent YAML 1.1 parsers from reading it as
  boolean false. Other language codes and existing operation IDs remain stable.

The old spec cannot be loaded by oasdiff because a schema `examples` value is a map.
The check normalizes that historical document's examples to an array and translates
its `nullable` intent to a JSON Schema type union before comparison. Normalization is
restricted to its exact SHA-256; the canonical new spec needs no preprocessing.

`0.3.0.json` records the exact oasdiff fingerprints associated with these corrections.
Some findings are duplicate effects across routes sharing one error schema, or
conservative reports for enum widening/reference extraction. They are not globally
ignored: all findings remain in the CI artifact, and any unlisted finding fails.
Approval of this PR includes review of this migration and its scoped manifest.

## Additions corrected relative to the supplied fragment

- Chat `response_format` is applied; named function choice and `reasoning_effort` are
  modeled. Optional numeric controls are clamped rather than rejected at static limits.
- Non-streaming `usage` is optional. The final opt-in SSE usage frame may have null
  usage. Cached/reasoning token detail models are included when measured.
- The chat body cap is 32 MiB and request budget is 1200 seconds. Mid-stream failures
  arrive as OpenAI error frames, followed by `[DONE]` while HTTP status stays 200.
- OpenAI billing errors and all three credential forms match the current router.
- V2 historical note records can omit fields; only their outer success envelope is
  universally required. V3 request/error models stay separate from V2.
- V3 allows at most one template source and rejects unknown keys/nulls. Its documented
  aggregate text and trimmed-title constraints still require server validation.

## Verification scope

Validation covers OpenAPI structure, local refs, duplicate keys/operation IDs, auth
requirements, nullability, and request model naming. Fixtures cover positive/negative
requests and representative response/error envelopes. Clean generated-client builds
check imports, serialization, two-header auth, multipart upload and template aliases.
These are local checks; production API availability, live credentials, billing,
WebSocket, SSE helpers and Python async behavior are not exercised by this spec PR.
